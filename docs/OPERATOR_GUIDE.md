# 维护者操作手册

本手册面向**值班维护者**，说明如何录入一场结果、确认整轮、公布对阵、
登记抽签、处理更正，以及如何发布和回滚。

配套阅读：[`RULES.md`](RULES.md)（规则与统计口径）、[`DEPLOYMENT.md`](DEPLOYMENT.md)（部署与排错）。

---

## 0 心智模型

```
data/event.json（唯一正式输入）
        ↓  本地维护工具录入
   导出变更包 JSON
        ↓  npm run data:import（校验基础版本）
   data/event.json 更新
        ↓  git commit + push
   GitHub Actions 校验并构建
        ↓
   公开快照 public/data/event.json → GitHub Pages
        ↓
      观众页面
```

**三条必须记住的边界：**

1. 维护工具的改动**先落在本地草稿**，不导出就等于没发生。
2. **导入成功 ≠ 已发布。commit 成功 ≠ 已发布。push 成功 ≠ 观众已看到。**
   只有 Actions 部署成功且公开页面 revision 变化，才算观众可见。
3. 同一赛事在本地编辑期间**由一名值班维护者负责**，避免两人同时改。

## 1 开始之前

```bash
git pull                      # 先同步仓库
npm ci                        # 安装锁定依赖（首次或依赖变化后）
npm run validate:data         # 确认当前源数据是健康的
npm run operator              # 启动本地维护工具（127.0.0.1:5199）
```

启动后终端会打印**维护工具入口**。也可以直接打开：

```
http://127.0.0.1:5199/operator.html
```

> ⚠️ **不要打开 `http://127.0.0.1:5199/`** —— 那是**只读的观众站**，
> 上面**没有任何录入表单**。录入页在独立的 `operator.html` 入口。
> `npm run operator` 会自动打开正确页面，并在终端打印这个地址。

维护工具会显示：

- **基础版本 revision** —— 你打开时的正式源版本。
  导出时会带上它，导入时用于冲突检测。
- 草稿校验状态（通过 / 有错误）。

> 维护工具只监听 `127.0.0.1`，公开站点**没有任何写入能力**。
> 生产构建中不包含维护模式的任何代码。

## 2 录入一场比赛（BO1 瑞士轮）

> **场地说明**：瑞士轮与决赛全部在**主舞台**进行。副场地A / 副场地B 只用于排位赛跑图。

1. 打开「**录入比赛**」标签页。
2. 左侧列表默认**按当天赛程排序**，可用**比赛 ID 或队伍名**搜索。
3. 点击目标比赛，右侧出现录入表单。
4. 填写：
   - 双方**积分**（原始积分，不封顶）
   - **到达最终积分的时间**（秒）
   - **胜者** —— 必须手动点选，**系统不会根据积分自动推断**
   - **异常类型** —— 见下表
   - 备注（可选）
5. 检查「**提交前摘要**」，确认无误后点「确认并写入草稿」。

### 异常类型怎么选

| 类型 | 何时使用 | 对统计的影响 |
| --- | --- | --- |
| **有效正常比赛** | 正常打完 | 双方计入 A/B/P/T、战绩、O |
| **按规则提前结束** | 有效但提前结束 | 同上 |
| **未开赛弃权** | 对手未到场等 | **不计入 A/B/P/T**；仍计入胜负与 O |
| **行政判负中止** | 行政判负/中止 | **不计入 A/B/P/T**；仍计入胜负与 O |

### 录入时的硬性要求

- **瑞士轮不允许平局**，必须指定胜者。
- **有效比赛必须填双方积分**。缺分**不等于 0**，不能用假 0 分填补。
- 积分不为 0 时**必须填时间**；积分为 0 时系统**自动记 360 秒**。
- 时间超过 360 秒会有提示，但**不会**因此判罚（原文未规定时间上限）。

### 重赛怎么办

直接照常录入。系统会：

- 把新结果作为**一次新的 attempt 追加**
- 把旧的有效记录标记为**被取代**
- **旧记录保留在数据里**（不删除），但**不再计入统计**

提交前摘要会提示「本场已有 N 次记录，提交将作为重赛追加」。

## 3 录入 BO3 小局

1. 打开「**BO3 小局**」标签页。
2. 左侧选择 `F-QUAL`（名额争夺战）或 `F-GF`（总决赛）。
3. 选择双方队伍（首次录入时）。
4. 选择**第几局**（已确认的局会置灰，系统自动跳到下一局）。
5. 填写积分、点选本局胜者，确认。

界面会**实时显示系列赛比分**，例如 `系列赛比分 1 : 0（先到 2 胜）`。

**重要：**

- 一方先到 **2 胜**，系列赛即结束。
- 剩余小局会被标为**「不需要进行」**，表单会阻止继续录入。
- 这**不是**「0–0 未完赛」，不要在别处按未完赛处理。

## 4 确认整轮与公布下一轮

### 4.1 确认整轮

打开「**轮次与配对**」标签页，表格显示每轮的「已确认场次 / 总场次」。

当某轮显示为 `8 / 8` 时，点「**确认整轮**」。

若还有未确认的场次，会明确列出是哪几场，无法确认。

### 4.2 生成候选

点该轮的「**生成候选**」。

- 系统按规则计算配对（R1 首尾配对；R2 起同战绩组内相邻配对）。
- 候选**只显示在工具里**，此时观众看不到任何变化。
- 如果存在阻断问题（例如某战绩组人数为奇数），会明确列出原因，
  **公布按钮会被禁用**。这种情况需要组委会处置，**不要手工凑数**。

### 4.3 公布并冻结

确认候选无误后，点「**公布这 N 场对阵并冻结**」。

这一步会：

- 写入比赛的参赛双方
- **冻结配对所依据的评分快照**（此后「当前参考排名」与「已用于配对的排名」分开）
- 把轮次标记为「已公布」

> **第三轮特别说明**：R3 全部 8 场**一次性公布**，跨日期间保持固定。
> 不要在 10 月 4 日早上根据前晚结果重新排序剩余四场。

## 5 录入排位赛

排位赛有两件事要录入，分别在两个标签页：

### 5.1 跑图成绩 ——「排位赛成绩」标签页

1. 左侧列表按轮次排列（可切换「两轮 / 第一轮 / 第二轮」），
   每条显示队伍、计划时间与场地。
2. 点选一条，右侧填写：
   - **积分**（参与排名的依据）
   - **到达最终分时间（秒）**（参与排名的依据）
   - **成绩文字**（可选）—— 例如「2.35 米」「完成」，仅作展示
   - **裁判备注**（可选）
3. 点「**保存并确认**」，或「仅保存（待确认）」。
4. 核分时段可点「**全部确认**」一次性确认所有待确认项。

> **保存并确认后名次会自动重排**，不需要手动拉顺序。
> 未确认（待确认）的成绩**不影响**对外名次。

### 5.2 名次口径（已由组委会确认）

1. **积分高者优**；
2. **积分相同时，到达最终分时间早者优**。

每队取**两轮中最优的一轮**参与比较（先比积分，积分相同再比用时）。

打开「**排位赛排名**」标签页可以看到由成绩实时算出的 1–22 名，
每一行显示该队的最优积分、用时、取自第几轮。

页面上会明确提示两种需要人工关注的情况：

| 提示 | 含义 | 处置 |
| --- | --- | --- |
| **N 支队伍暂无积分成绩，已排在榜尾** | 这些队还没有可比较的成绩 | 补录成绩后自动重排 |
| **积分与用时完全相同的并列** | 数据无法区分先后 | 用「人工覆盖」指定顺序，或按组委会决定处置 |

> 「只录到一轮」**不算**没有成绩：那一轮就是它的最优成绩，正常参与排名。

点「**采用这个名次并写入草稿**」即写入。

### 5.3 人工覆盖（仅在必要时）

自动名次无法表达组委会决定时（例如并列需指定先后），
在「人工覆盖」区点「以自动名次为起点，手动微调」，用 ↑ / ↓ 调整，
填来源说明，点「确认人工名次并写入草稿」。

**校验规则**：排名必须包含**全部 22 支竞技组队伍**、**不重复**。

> 场地是 A/B 两个副场地，**并行**跑图；每队两轮各用一个不同场地（互换）。
> 瑞士轮与决赛不在副场地，全部在主舞台。

### 5.4 原始成绩是公开的

全部 44 次跑图的**原始成绩**（积分、到达最终分时间、成绩原文、场地）会在
公开站点展示两处：

- 「晋级 → 排位赛」页的**跑图记录**表，并标出每队哪一轮「计入名次」；
- 每支队伍的**详情页**，列出它自己两轮的原始成绩。

因此录入时请确保积分与用时准确 —— 它们既决定名次，也会被观众直接看到。

## 6 公布八强种子

打开「**八强种子**」标签页，点「计算并公布八强种子」。

**前置条件**：**第五轮必须已确认**。
否则会拒绝并提示「最终种子必须等第五轮全部结束后统一计算」。

系统按规则映射：

- `3-0` 组前两名 → `W1`、`W2`
- `3-1` 组前两名 → `W3`、`W4`，第三名 → `L1`
- `3-2` 组三名 → `L2`、`L3`、`L4`

若战绩组人数不足（例如 `3-0` 只有 1 队），会拒绝并报明原因。

## 7 登记展示组抽签

打开「**展示组抽签**」标签页。

1. 按抽签结果用 ↑ / ↓ 排列（**第 1 位最先上台**）。
2. 点「登记抽签顺序」。

排好之后，三个展示组队伍详情页会显示各自的正式演出时间；
**在此之前页面显示「等待抽签」，不会推测上台顺序**（绝不沿用编号顺序）。

## 8 公告与时间调整

### 添加公告

「**公告与时间**」标签页 → 填写标题、内容、级别（信息/注意/重要）→ 添加。

用于发布「时间仅供参考，以现场通知为准」这类现场信息。

### 调整时间

1. 选择日程项。
2. 填写**修订后开始时间**，必须是带偏移的 ISO 8601：
   `2026-10-03T09:10:00+08:00`
3. 填写调整说明。
4. 保存。

> **原计划时间保持不变**，修订时间单独记录，日程调整**不破坏结果身份**。

## 9 导出与发布

### 9.1 一句话版本

```bash
npm run operator                          # 1. 打开工具，录入
#                                          # 2. 点「下载变更包 JSON」
npm run publish -- --file <导出文件> -m "说明"   # 3. 剩下的全自动
```

`npm run publish` 一条命令替你完成：
**导入 → 校验 → 生成公开快照 → 提交 → 推送（自动重试）**。

任何一步失败都会**立即停止并回滚** `data/event.json`，不会留下半成品。

### 9.2 导出变更包

打开维护工具的「**导出与发布**」标签页：

1. 确认「发布前检查」显示**通过**。
   有错误时必须先回到对应标签页修复。
2. 点「**下载变更包 JSON**」。
   下载失败时，下方文本框可直接复制全文。

变更包是**完整赛事版本**（不是局部补丁），
外层包含 `baseRevision`（你打开时的正式源版本），用于冲突检测。

### 9.3 一条命令发布

```bash
# 正式发布（导入 + 校验 + 构建 + 提交 + 推送）
npm run publish -- --file ~/Downloads/rg26-change-20261003.json -m "R1 结果确认"

# 先预览，不提交（推荐第一次用这个确认无误）
npm run publish -- --file <文件> --dry-run

# 只提交不推送（想自己检查再推）
npm run publish -- --file <文件> -m "说明" --no-push
```

`-m` 的说明会作为 commit message，**写清改了什么**（轮次、更正原因）。

### 9.4 命令做了什么

| 步骤 | 动作 | 失败时 |
| --- | --- | --- |
| 1 | 导入变更包（核对 `baseRevision`） | 源文件**不变** |
| 2 | 校验数据 | **回滚**到导入前 |
| 3 | 生成 `public/data/event.json` | **回滚** |
| 4 | `git add` + `git commit` | **回滚** |
| 5 | `git push`（失败自动重试 4 次） | 提交已在本地，稍后 `git push` 即可 |

**基础版本冲突**（别人先改过）时会被拒绝且不提供强制覆盖。
处理方式：`git pull` → 重新打开维护工具 → 人工重新录入 → 重新导出。

### 9.5 确认观众已看到

命令跑完后**还没结束**：

1. 打开仓库 **Actions** 页面，等 `Deploy to GitHub Pages` 变绿（通常 1–3 分钟）。
2. 打开公开站点，确认底部/顶部的**数据更新时间**已变化。
3. 抽查受影响的比赛或排名。

> **push 成功 ≠ 观众已看到。**
> 导入、commit、push 三者成功都只代表改动离开了你的电脑。

### 9.6 想手动执行的话

每一步也可以单独跑：

```bash
npm run data:import -- --file <文件>   # 只导入
npm run validate:data                  # 只校验
npm run data:build                     # 只生成公开快照
npm run dev                            # 本地预览
git add data/event.json public/data/event.json
git commit -m "说明"
git push
```

## 10 更正已确认的成绩

更正必须走完整个流程，**不能直接改 JSON 假装没发生过**。

1. 在维护工具中录入更正后的结果（作为新的 attempt）。
2. 导出变更包，用 `npm run data:import` 导入。
3. 系统会给出**影响面分析**，按情形要求处置：

| 情形 | 系统行为 | 你需要做的 |
| --- | --- | --- |
| **下游尚未发布** | 重算评分并重建候选 | 重新生成并公布候选即可 |
| **下游已发布但未开赛** | **阻止导出**，列出受影响轮次 | 依据裁判/组委会决定：选「保留已公布对阵并说明」或「作废并重新公布」 |
| **下游已开赛或有有效结果** | **阻止自动推进**，保留既有比赛记录 | 记录组委会修订结果后才能恢复发布 |

4. 在 `event.corrections` 中记录：原因、时间、旧值、新值、受影响对象、处置方式。

### 为什么重算范围这么大

瑞士轮评分**跨队伍依赖历史对手**。
更正任何一场成绩都要：

1. 重算**该截止轮次的全部队伍**（不只是被更正的两队）
2. 再比对**所有后续已公布轮次和最终种子**

决赛则沿 `winner`/`loser` 依赖图检查**全部受影响下游**。

> **绝不**把旧比分静默移给另一支队。
> 已经发生的比赛记录必须保留原样，并标记依赖不一致。

## 11 冲突与常见问题

### 「基础版本不一致，拒绝覆盖」

**原因**：你打开维护工具后，仓库里的 `data/event.json` 被别人改过。

**处理**：

1. `git pull` 同步最新版本
2. 重新打开（或刷新）维护工具，载入新的正式源数据
3. **人工重新录入**你的改动
4. 重新导出

**不要**试图绕过 —— 没有 force 选项是刻意设计的。

### 「草稿保存失败」

浏览器存储空间不足或被禁用（隐私模式）。

**处理**：**立即导出变更包**，否则改动会丢失。在线浏览不受影响。

### 「存在未处置的更正，拒绝导出」

`event.corrections` 里有 `disposition: "pending"` 的更正。

**处理**：完成 §10 的处置流程，把 `disposition` 改为具体处置方式。
可在「导出与发布」页看到具体是哪条。

### 「某战绩组人数为奇数，停止自动配对」

通常是退赛导致的。

**处理**：**不要擅自轮空或手工凑数**。
报请组委会公布处置决定，并把修订说明写入该轮的 `revisionNote`。

### 观众说「看不到最新结果」

按顺序检查：

1. Actions 是否部署成功？（失败时会阻止部署）
2. 公开站点的**数据更新时间**是否变化？
3. 让观众点「立即刷新」，或等待最多 60 秒自动检查。
4. 若长时间未更新，可能是 CDN 传播延迟；等待几分钟后重试。

## 12 回滚

**用新的 commit 发布，不要 reset 历史。**

```bash
git log --oneline data/event.json          # 找到已知正确的版本
git checkout <正确的 commit> -- data/event.json
npm run validate:data && npm run data:build
git add data/event.json
git commit -m "回滚到 <commit>：<原因>"
git push
```

> 客户端会接受「内容哈希变回旧值但发布信息已更新」的合法回滚，
> 不会仅凭内容相同就认定「已经检查过」。

## 13 发布前检查清单

- [ ] `npm run validate:data` 通过（只剩「场地名为占位」这类已知提示）
- [ ] `npm run test` 全部通过
- [ ] `npm run data:build` 成功生成公开快照
- [ ] 本地 `npm run dev` 抽查受影响的队伍与对阵
- [ ] 提交信息说明了轮次或更正原因
- [ ] 没有未处置的更正（`disposition: "pending"`）
- [ ] 没有把测试数据（`tests/fixtures/`）混进正式数据
- [ ] 部署后已在公开页面核对 revision 与结果
