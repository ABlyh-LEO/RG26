## 1 时间与权威性

原文明确说明：**以下时间仅供参考，具体情况以赛程组共享文档当天安排为准。**
目前未提供该共享文档地址（记录在 `event.openItems`）。

本工具的行为约定：

- 所有时间以带时区偏移的 ISO 8601 存储（例如 `2026-10-03T09:00:00+08:00`）。
- 显示一律按赛事时区 `Asia/Shanghai`，**不跟随访问者所在时区**。
- 当地时间经过计划开始点，**不会自动**把比赛标记为「正在进行」或「已结束」。
  这种情况显示为「等待现场确认」。
- 计划时间、修订后的计划时间、实际时间三者分开存放，日程调整不破坏结果身份。
- 结束时间未知时为 `null`，**绝不编造**占位时刻；依赖关系用 `afterSeriesId` 表达。

## 3 瑞士轮统计口径

### 3.1 两种统计集合（必须严格分开）

对每队：

| 符号 | 含义 |
| --- | --- |
| `n` | 计入得分表现的**有效比赛**数量 |
| `m` | 已结算并登记的**对阵**数量（含未开赛弃权与行政判负中止） |
| `W`、`L` | 上述对阵的胜负数量 |
| `s_k`、`o_k` | 第 k 场本队 / 对方的**最终有效原始积分**（不封顶写回） |
| `d_k` | `s_k − o_k` |
| `t_k` | 开赛后首次达到最终有效积分的时间（**建筑须经稳定确认**）；零分局记 360 秒 |

| 结果类型 | 计入 A/B/P/T | 计入 W/L、m、O |
| --- | --- | --- |
| `normal` 有效正常比赛 | ✅ | ✅ |
| `early-end` 按规则提前结束 | ✅ | ✅ |
| `walkover-before-start` 未开赛弃权 | ❌ | ✅ |
| `administrative-stop` 行政判负中止 | ❌ | ✅ |

**是否计入由结果类型推导**，不靠手工勾选组合，避免出现互相矛盾的记录。

### 3.2 「已登记对阵」的口径

按**已经确认结果**的有效对阵计入本次结算。
下一轮**仅公布但尚未完赛**的配对**不提前计入 O**。

> 这是本工具的解释（原文写「m 为已登记对阵场数，按每场对应对手计入一次」）。
> 若组委会有不同解释，应递增 `rules.version` 并调整本节。

### 3.3 关键约束

- 瑞士轮**每场必须有明确胜者，不允许平局**。
- 胜者**由裁判确认**，不根据积分高低自动推断。
  维护工具把「建议胜者」与「正式胜者」分开。
- **缺分不等于 0**，不得用假 0 分填补缺失数据。
- 重赛只纳入**最后有效**的那一次；旧记录保留并标记为被取代。
- 输入积分与秒数用规范化非负十进制字符串存储并保留实际精度；
  拒绝负数、非数字、非有限值；**原始积分不设 16 分上限**。
- 时间大于 360 秒只提示复核，**不据此新增硬性判罚**（原文未明确时间字段总范围）。

## 4 公式

以下公式已对照 DOCX 内置数学结构（OMML）逐项核读。

```text
局均得分 = Σ s_k / n
局均分差 = Σ d_k / n
T       = Σ t_k / n

A = (100 / n) × Σ( min(s_k, 16) / 16 )
B = (1 / n)   × Σ( 50 + 5 × clamp(s_k − o_k, −10, +10) )
P = (A + B) / 2

v_j = W_j / (W_j + L_j)
q_j = 50 × v_j + 0.5 × P_j
O   = (1 / m) × Σ q_j        （按每场对应对手计入一次）
R   = 0.6 × P + 0.4 × O
```

### 计算顺序

1. 先计算**所有**队伍的 `P` 与 `v`。
2. 再遍历对手记录计算 `O`、`R`。
   `O` **不依赖**对手的 `O` 或 `R`，因此是单遍的。

### 边界值

| 条件 | 结果 |
| --- | --- |
| `n = 0` | `A = B = P = 0`，`T = 360` |
| 无胜负记录 | `v = 0` |
| `m = 0` | `O = 0` |
| `n = 0` 时的局均得分/分差 | 显示「—」（原文未规定默认值） |

`A`、`B`、`P`、`O`、`R` 均在 0–100 之间。

### 原文简例（作为回归测试 D01）

某队两局积分为 18、0，对手为 12、10：

- 分差为 `+6`、`−10`
- `A = (100 + 0) / 2 = 50`（18 封顶为 16 → 100；0 → 0）
- `B = (80 + 0) / 2 = 40`（`+6 → 50+30=80`；`−10 → 50−50=0`）
- `P = 45`
- 若两名对手的胜率为 `0.5`、`1`，`P` 为 `60`、`70`，
  则 `q` 为 `55`、`85`，`O = 70`，`R = 0.6×45 + 0.4×70 = 55`

该例已实现为自动化测试（`tests/domain/scores.test.ts`）。

### 数值精度

- 在 `src/domain/rational.ts` 中实现小型有理数运算：
  规范化 BigInt 分子/分母、十进制字符串解析、加减乘除、比较、显示格式化。
- 公式里的 `0.6`、`0.4`、`0.5` 分别使用 `3/5`、`2/5`、`1/2`。
- **比较使用交叉相乘**，不用 epsilon 把不等值强行视为相等。
- **只在展示阶段保留两位小数**，排序一律使用原始计算精度。
- 序列化时把分子/分母转为字符串（不能直接 `JSON.stringify` BigInt）。

## 5 排序与配对

### 同战绩组排序

依次比较，**前项相同才比较后项**：

1. `R` **高**者在前
2. `P` **高**者在前
3. `T` **小**者在前
4. 排位赛最终名次**靠前**者在前

按原始精度排序，公布时保留两位小数。
**页面显示的四舍五入值不参与排序。**

不增加未规定的「直接交手」「净胜分优先」等规则。

### 配对

- **R1**：按正式排位首尾配对 —— 第 1 名对第 16 名、第 2 名对第 15 名……第 8 名对第 9 名。
- **R2 起**：按相同胜负战绩分组，组内按上述规则排序，
  依次「第 1 名对第 2 名、第 3 名对第 4 名」相邻配对。

配对组顺序（按赛程初始化）：

| 轮次 | 组顺序 | 正常场次 |
| --- | --- | --- |
| R2 | `1-0`、`0-1` | 4 + 4 |
| R3 | `2-0`、`1-1`、`0-2` | 2 + 4 + 2 |
| R4 | `2-1`、`1-2` | 3 + 3 |
| R5 | `2-2` | 3 |

组内场次顺序就是排序后的相邻配对顺序。

### 停止条件与轮次门禁

- 达到 3 胜或 3 败后**停止参赛**。
- 每一轮**全部结束且确认后**才生成下一轮正式候选。
- 正常场次预期为 `[8, 8, 8, 6, 3]`，**不能为了凑数伪造比赛**。
- 若退赛等导致某组人数为奇数、名单异常或名额变化：
  **停止自动配对并显示原因**，允许有说明的组委会修订，**不擅自轮空**。
- 原文**没有**「避免重复对阵」的规定，因此**不实现**自动避重、跨组调队、随机配对或轮空。

### 第三轮跨日冻结

R3 必须在 **R2 确认后一次性发布全部 8 场对阵和时间槽**。
不得在 10 月 4 日早上根据前晚四场结果重新排序剩余四场。

### 赛程图展示约定

「瑞士轮→决赛」页签把瑞士轮 5 轮与决赛画成**一条从左到右的线**：
列为阶段、卡片纵向堆叠、SVG 连线表示晋级流向。

**该图不含排位赛。** 排位赛是 44 次单队跑图，与瑞士轮没有逐场对应关系
（只是"前 16 名晋级"），一列就有 5000px 高，画进去会把整张图压垮。
排位赛见独立的「排位赛」页签。

**分列按比赛轮次，不按胜者组/败者组。** 八强首轮四场（`F-W1A`、`F-W1B`、
`F-L1A`、`F-L1B`）属于**同一轮**，放在同一列：

```
八强赛 → 败者组第二轮 → 半决赛 → 名额争夺战 → 总决赛
```

原因是这四场交叉向前喂给下一轮（`F-L1B→F-L2A`、`F-L1A→F-L2B`、
`F-W1A→F-WSF`、`F-W1B→F-WSF`）。若把胜者组与败者组拆成左右两列，
这四条连线就会各自横穿一整列无关卡片，看起来像"连错了"。

#### 实现时必须守住的五条约束

这五条都是踩过坑才定下来的，改动 `BracketChart.tsx` / `bracket.css` 时不要破坏：

**1. 画布高度只能偏高，不能偏低。** 取
`Math.max(layout.totalHeight, measuredHeight, FALLBACK_HEIGHT)`。
`heights` 状态永远是上一帧的值，而窄屏下列宽收敛到 `minColumnWidth`、
卡片变窄、队名多换一行，真实高度会超过记录值。更麻烦的是
`overflow-x: auto` 会让浏览器把 `overflow-y: visible` **提升成 `auto`**，
一旦算矮，最下面一场比赛就被直接裁掉**而且滑不到**。
多几个透明像素无所谓，少一个像素就是一场比赛看不见。

**2. 列宽只能从滚动容器量，不能从 board 量。** board 的宽度正是由列宽
算出来的，用 `board.clientWidth` 会形成"测量→改宽→再测量"的正反馈，
宽度会一轮轮放大（曾膨胀到 914 万像素）。一律取 `scroller.clientWidth`。

**3. 列 body 高度用本列的值**（`layout.columnHeights[key]`），
不能用全局最大高度：节点是绝对定位在 body 内的，矮列的 body 被撑高就会
溢出画布，视觉上糊成一团。

**4. 两种颜色的线必须能分辨。** 胜者实线（蓝）与败者虚线（橙）会在同一
通道里交叉，因此先画一层**背景色外衣**（`.bracket__link-casing`）再画彩线，
让交叉处的下层线"断开"一小段；线要细（1.5px，≥900px 为 1.75px）、
通道要宽（`GAP = 64`）、同一通道内的多条线按 `laneOffset()` **严格单调**
铺开，任意两条车道的 x 必须互不相同。

**5. 横穿段也要分车道——而且"每一段横线"都要分，不能只管横穿段。**

这是 **5** 条里唯一必须按**两个轴同时**理解的约束，也是最容易漏的一条：

- 车道（`laneCount`）只管**竖直段**的 x。两条线的竖段若共用同一个 x，
  会重叠成一条，看起来像"少了几条线"。
- 但图上最严重的重叠从来不在竖段，而在**同高度的水平段**：
  两段横线落在同一个 y、区间还互相覆盖时，**看起来只有一条线，
  却代表两条不同的晋级路径**。基线实测 12 处，最长一处重叠 **250px**。

因此**每一段横线都要经过 `reserveHorizontal(通道 x, 高度 y, 步长)` 登记占用**，
包括进入段、横穿段、离开段：

- **占位键必须是 `(通道, 高度)`**，不能只按高度。不同通道的同高度横线
  在图上分得很开，不该互相排挤。
- **进入段最容易被忽略**：`F-W1A→F-WSF` 从八强赛 (cy 370.99) 出发，
  而「败者组第二轮」的 `F-L2B` 恰好也在 cy 370.99，
  于是"离开 F-W1A 的横线"与"进入 F-L2B 的横线"在 x=1376..1440
  通道里完全重合。只给横穿段分车道**改不到它**。
- **跨列连线与相邻列连线必须共用同一套 `laneCount`**。两套计数各自从 0
  开始，会算出同一个 x，实测产生 74px 的竖直重叠。

**评分要包含"腾挪后的落点"，不能先挑最好的再硬挪。** 先按
`|候选 - 理想高度|` 挑中候选、再交给 `reserveHorizontal` 让位，
该候选被占用时会被推到最远 `MAX_HORIZONTAL_TRIES × CLEAR = 720px` 之外：
实测把 `F-W1B→F-WSF` 顶到 y=265（要跨过第 5 场），绕行比冲到 **2.27**
并多出一次竖直折返——比修复前的 1.41 还糟。
正确做法是对每个候选先算它腾挪后**实际会落在哪里**，再按该落点评分。

**唯一允许的共线重叠**是「同一张卡片发出的两条边」或「汇聚到同一张卡的
两条边」（胜者与败者从同一场比赛分出，共用卡片边缘中点，几何上无法分开）。
除此以外任何共线重叠都是缺陷，由 e2e 用例
「连线不重叠：不同路径的水平段不得共线重叠」守住——
**这条断言补上之前，不得声称连线已修好**。

| 第 2 场 | 八强败者组首轮 B | 第 7 场 | 半决赛败者组 |
| 第 3 场 | 八强胜者组 A | 第 8 场 | 半决赛胜者组 |
| 第 4 场 | 八强胜者组 B | 第 9 场 | 总决赛名额争夺战 |
| 第 5 场 | 败者组第二轮 A | 第 10 场 | 总决赛 |

**对外一律用序号，不用内部 ID。** 未决出的名额写「第 3 场败者」，
不写 `F-W1A 败者` —— 后者是程序内部标识，在赛程表和现场公告上都找不到对应。
卡片标题同样带序号（如「第 5 场·败者组第二轮 A」），方便对照。

展示组演出与表演赛不属于竞技赛程，不参与编号。

### 对阵未确定时如何展示

赛程图上还没确定的对阵，**必须说明"在等什么"**，不能填一个看起来像真的名次。

| 情况 | 数据表达 | 界面显示 |
| --- | --- | --- |
| 上一轮结果未确认 | `slotRef` = `pending` + 原因 | 「等待第 1 轮结果确认后公布」等 |
| 依赖某个系列赛 | `winner` / `loser` | 「第 8 场败者」 |
| 八强种子未公布 | `finals-seed` | 「W1」「L4」 |
| 排位赛名次已锁定 | `qualification-rank` | 「排位赛第 3 名」 |

要注意 **`qualification-rank` 只在名次真正锁定后才用**。瑞士轮尚未公布时，
整列不该出现「排位赛第 1 名 vs 排位赛第 2 名」这种配对 —— 那不是赛程，
只是把槽位编号念了一遍。

### BO3 小局

- 小局与系列赛**分开记录**。
- 每局确认胜者后累加系列赛比分，**先达到 2 胜即结束**。
- `2–0` 后第三局标记为**「不需要进行」**，不能当作 0–0 未完赛。
- **不能在系列赛尚未产生胜者时向下游推进。**

### 已晋级/淘汰队伍的指标

已晋级、已淘汰队伍的**胜率和 P 按实际已赛成绩保留**，
其 `O` 仍随历史对手后续成绩更新。

**因此两支 3-0 队伍不能在 R3 当晚就永久确定 W1/W2** ——
最终种子要等 **R5 全部结束后**统一计算。

## 7 状态与更正机制

### 三个独立维度

| 维度 | 取值 |
| --- | --- |
| `executionStatus`（现场进程） | `scheduled` / `ready` / `running` / `finished` / `delayed` / `cancelled` / `not-needed` |
| `resultStatus`（结果） | `none` / `provisional` / `confirmed` |
| `publicationStatus`（公布） | `draft` / `published` / `superseded` |

- 维护工具中的**草稿只保存在本机**。
- 正式站点的数据只能来自**通过校验并发布**的快照。
- 观众可以看到明确标注的「待确认成绩」，
  但它**不能参与正式配对或晋级**。
- 当地计划时间已过，**不得自动**把比赛标成正在进行或已结束。

### 轮次确认与冻结

每轮保存：轮次 ID、`matchIds`、输入截止轮次、该轮结果版本、确认时间、
**配对所依据的评分快照**、配对版本、公布时间、分组与槽位。

把「当前参考排名」和「已用于正式配对的排名」**分开**。

维护流程：

```
录入成绩 → 单场确认 → 全轮校验与确认 → 生成下一轮候选 → 检查 → 公布并冻结
```

网站可以自动算出候选，但**不能因为一次输入保存就自动对外宣布新的对阵**。

### 更正的三类情形

1. **下游尚未发布** —— 重算评分并重建候选，作废旧候选。
2. **下游已发布但未开赛** —— 先显示受影响范围，要求维护者依据裁判/组委会决定选择
   「保留已公布对阵并说明」或「作废旧版本并重新公布」。
   **没有处置记录时阻止导出正式版本。**
3. **下游已经开赛或有有效结果** —— 保持已经发生的参赛双方和比赛记录，
   **不能静默把旧比分移给另一支队**。标记依赖不一致并阻止自动推进；
   记录组委会修订结果后才可恢复发布。

### 跨队伍重算范围

瑞士轮评分跨队伍依赖历史对手，因此更正时必须：

1. 重算**该截止轮次的全部队伍**（不只是被更正的两队）。
2. 再比对**所有后续已公布轮次和最终种子**。

决赛则沿 `winner`/`loser` 依赖图检查**全部受影响下游**。

采用**一个新的赛事数据版本整体保存**更正和处置，
不留下「新比分配旧种子但无说明」的半状态。
取消、重赛和行政结果用明确类型表达；**不删除历史数据后假装从未发生**。

## 8 原文未明确、采用安全默认的部分

以下内容原文没有规定。本工具**不自行推测**，采用显式默认值：

| 事项 | 安全默认 | 影响 |
| --- | --- | --- |
| 排位赛两轮「最优成绩」的比较规则与同分打破 | 录入**裁判确认的 1–22 名最终排序** | 不按积分、用时或三审排名自行排序 |
| 原始成绩的结构 | 允许保存结果文字与可选积分/用时 | 它们**不参与**自动确定排位名次 |
| 「已登记对阵 `m`」是否含仅公布未开赛的配对 | **不含**（只含已确认结果的） | 影响 O 的计算；见 §3.2 |
| 时间字段的总范围 | 大于 360 秒只提示复核 | 不据此新增硬性判罚 |
| 避免重复对阵 | **不实现** | 原文没有该规则 |
| 真实场地名称 | 主舞台 / 副场地A / 副场地B | ✅ 已确认，`provisionalName: false` |

### 尚未补齐的资料

记录在 `data/event.json` 的 `event.openItems`，并与页面上同步展示：

1. 赛程组共享文档地址（原文声明以其当天安排为准）
2. 是否公开原始 DOCX
3. 展示组决赛抽签顺序（10 月 3 日 12:00 抽签后录入）

缺少这些资料不妨碍本地开发，使用**明确的待定值**，**不虚构**。
