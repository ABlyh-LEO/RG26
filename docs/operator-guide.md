# 维护者操作手册

当前赛程以本目录的 `RoboGame2026赛程安排（暂定） (1).docx` 为准；竞技规则参照 `RoboGame2026 竞技组规则手册4_6.pdf`。根目录旧赛程仅作历史资料，不能作为录入依据。规则口径和待确认项见 [RULES.md](RULES.md)，首次配置 Pages 见 [DEPLOYMENT.md](DEPLOYMENT.md)。

## 1 启动与交接

需要安装 Git 与 Node.js（版本按仓库 `.nvmrc`），并预先配置好 Git 提交身份和该仓库的推送权限。首次使用在仓库运行 `npm ci`。Windows 可双击根目录 `start-operator.cmd`，也可以运行：

```bash
npm run operator
```

浏览器会打开 `http://127.0.0.1:5199/operator.html`。保留启动终端；关闭浏览器不会停止后台服务，关闭终端会停止它。重新运行命令可恢复已经保存的草稿与发布任务。

首次接班，在“发布记录 → 交接、同步与应急工具”中同步远端正式数据。同步要求没有未发布草稿或未完成输入，且 main 工作区干净；工具仅执行快进同步。已有草稿时先下载备份，处理完当前工作后再同步。

第二个浏览器页面默认只读。点击“接管编辑”后，原页面会变为只读；未能保存的窗口输入可以下载备份。不要由两台电脑同时维护同一场赛事；若远端先有更新，发布会停止并保留本机草稿。

## 2 保存与发布是两个动作

输入会自动保存到当前电脑的 `.local/operator/`，包括未填完的表单、已经确认但尚未发布的结果、操作记录和发布任务。看到“草稿已自动保存”后再关窗口；保存失败时先下载窗口草稿备份，再处理错误。此目录由 Git 忽略，不会进入公开网站。

“保存并确认结果”只把裁判已确认的结果放入本地草稿。观众会在完成“预览与发布”后看到正式变化。未完成的表单不会被当成比赛结果发布，发布其他场次也会保留这些输入。

正式输入只有 `data/event.json`。工作台直接读取它，不从可能滞后的公开快照加载正式基线。不要用 `npm run data:seed` 重置正在使用的赛事。

## 3 录入比赛

在“赛事工作台”按日期、状态筛选，或搜索队伍和场次。列表按日程排列，选择场次后自动显示对应阶段的表单，再按界面标出的红蓝方录入；BO3 的每一局分开保存，结束后无需进行的小局会停止录入。

1. 填写积分及到达最终分时间；排位赛可以补充成绩文字和裁判备注。
2. 两队对抗须由维护者依据裁判记录明确选择胜者，软件不会替代裁判判断。
3. 选择正常比赛、提前结束、弃权或行政判负等实际结果类型。
4. 点击“保存并确认结果”，或“保存并录入下一场”。排位赛尚待复核时可“保存为待确认”。

有效比赛缺少积分或必填时间时，会在具体字段提示。缺分不等于零分；零分时间沿用现有 360 秒约定。比赛日程时间只用于安排，不能自动推定比赛已经开赛或结束。

已确认结果需要修改时，明确选择“更正”或“重赛”，填写原因，分析排名与下游对阵的影响，再选择处置方式。已开赛的下游需要记录组委会决定；不得把旧结果直接移给变化后的对阵。旧值、新值和原因会保留。未处理的更正会阻止发布。

## 4 排名、配对与现场日程

在“对阵与排名”完成以下工作；每项操作同样先进入草稿：

- **排位赛排名**：检查由已确认成绩算出的名次；并列或组委会决定需要人工覆盖时，注明来源。
- **瑞士轮配对**：确认整轮结果，生成候选，检查后公布并冻结。门禁不通过时处理列出的具体场次，不手工凑对阵。
- **八强种子**：等第五轮全部确认后计算并公布，不能用尚未结束的参考排名代替最终种子。
- **展示组抽签**：按正式抽签结果登记顺序，未登记前保持待定。

“公告与日程”可添加公告、填写北京时间修订时间和调整原因。原计划时间保留，修订安排作为独立信息显示。当前完整赛程与全部决赛依赖见 [RULES.md](RULES.md)，勿沿用旧版的 R3 跨日安排或决赛场数。

## 5 统一发布

进入“预览与发布”：

1. **核对累计变更**：逐项查看原值与新值，处理错误提示。
2. **生成观众预览**：预览使用与公开站点相同的页面和数据推导，冻结本次草稿版本。
3. 填写本次发布说明，勾选已核对确认，再点击“确认发布”。预览后继续修改草稿，需要重新生成预览。
4. 查看发布记录，等待“观众已可见”。开始推送后可以继续录入下一批草稿，上一批完成后再发布下一批。

发布顺序是：检查源版本和 Git 环境 → 保存正式数据与快照 → 只提交赛事数据文件 → 推送 → 等待 Pages 部署 → 核对公开站点。

发布要求当前在 main，已配置 origin，且没有与赛果无关的工作区或暂存区修改。main 已有其他未推送提交时也会停止，需先单独处理这些提交，避免夹带发布代码。工具不会替你提交其他文件，也不强制推送。代码尚在修改时仍可录入和预览，环境问题只阻止发布。

Pages 通常需要等待几分钟。只有公开 `data/event.json` 同时返回本次内容版本 **revision** 和对应 **sourceCommit**，任务才显示“观众已可见”。推送成功、Actions 成功都不是单独的上线判据。GitHub API 限流时，工作台仍会检查公开快照。

自定义域名或无法由 origin 推断的站点，可在启动进程前设置 `OPERATOR_PAGES_URL` 为真实 HTTPS 站点地址。网络连接沿用已有 Git 或环境代理，Windows 下还会检查当前系统代理；仅对当前子进程生效，不修改全局代理，也不内置个人代理端口。

## 6 失败与恢复

| 情况 | 数据状态与处理 |
| --- | --- |
| 校验失败、源版本变化、远端已经更新 | 不创建发布提交，草稿保留。先备份，核对差异；需要同步时明确放弃旧基线草稿后同步，再人工合并。 |
| 写文件或提交前失败 | 恢复发布前正式源、公开快照和数据文件的暂存状态；草稿保留，可修正后重新预览。 |
| 提交成功但推送失败 | 本地提交保留。点击“从失败阶段重试”会重推同一提交，不重复提交，不回滚已提交记录。 |
| 推送成功但部署失败 | 查看部署记录修复具体问题；可在 Actions 重跑相同提交，工作台继续核对公开版本。 |
| 工具进程在发布中退出 | 重启后读取任务与事务备份：未提交的恢复原文件；已提交的识别提交并提供重推。 |
| 保存时遇到版本冲突或编辑会话被接管 | 先备份此窗口草稿，再载入服务端草稿；不要不断重试旧版本覆盖他人输入。 |
| 状态停在等待部署且 API 不可用 | 保持工作台运行或稍后重开；可点击“检查上线状态”，并从部署链接检查实际运行。 |

发布检查期间不要在同一仓库手工修改 Git 分支或赛事文件。若工具发现 Git 已变化，会停下并保留恢复信息供核对。

## 7 备份、迁移与命令行

日常使用不需要导出文件。“下载完整本地草稿”用于交接和应急备份，包含未完成表单；“导入交接文件”恢复本地工作，必须核对与当前正式版本的差异。旧浏览器草稿只在明确选择导入后迁移；核对前不能发布。

保留现有变更包命令行入口供技术维护者使用。该入口接受 `schemaVersion/baseRevision/exportedAt/event` 格式的变更包，与完整工作台草稿备份不同：

```bash
npm run publish -- --file <变更包.json> --dry-run
npm run publish -- --file <变更包.json> -m "第一轮结果确认"
npm run publish -- --file <变更包.json> -m "检查本地提交" --no-push
npm run publish -- --retry <任务ID>
```

`--dry-run` 只读取并输出校验、变更和发布环境阻碍；不会改源、快照、暂存区，也不会创建本机草稿。`--no-push` 生成本地提交并保留任务，随后用 `--retry` 推送同一提交。实际命令行发布前须关闭正在使用本仓库的工作台服务，避免双进程写入；只读 dry-run 可并行执行。

不要用 `reset --hard` 抹去已经公布的错误。赛事结果的更正通过工作台新增可追溯记录；整份数据的紧急回退须由技术维护者检查后，以新提交发布，并重新核对观众页面。
